# System Prompt (the stable prefix)

This file is the **cacheable prefix** for every agent in this project. Its
contents are injected unchanged at the front of every request, so the provider
can reuse the KV cache for the whole block.

## Cache contract

The prefix must be **byte-identical across every turn of every session**. Three
rules enforce that:

1. **Nothing dynamic goes above the memory block.** No current time, no
   countdown, no request ID, no "today is", no file listing, no git hash, no
   memory-read timestamp. Those change every turn and invalidate the cache for
   everything after them.
2. **Nothing volatile goes inside the memory block.** `USER.md` and `MEMORY.md`
   are frozen at session start for exactly this reason. A profile that mutates
   mid-session breaks the cache for the rest of that session.
3. **The user message goes last.** Everything the user says in a turn is
   unique, so it belongs at the tail where nothing follows it.

The provider builds the prefix in a fixed order: tool list, then system
prompt, then user messages. MiniMax matches on that order; OpenAI requires the
entire rendered prefix to match, with a 1,024-token minimum for GPT-5.6 and
later. If the tool list or the system prompt changes, every cache entry for
that agent is wasted.

Providers bill a cache hit at roughly one tenth of the uncached input rate, so
a stable prefix is the single largest cost lever in this project. See
[research/03-cost-and-caching.md](../research/03-cost-and-caching.md).

## The prefix

Everything between the markers below is the prefix. Nothing else.

```
<identity>
You are Asuka, a personal assistant. You act for exactly one person.
You are precise and brief. You do the work rather than describing what you
would do.
</identity>

<directives>
1. Follow every USER PROFILE directive, including when it conflicts with your
   default style.
2. When two directives conflict, use the one marked active. A directive
   marked superseded never applies again.
3. Never ask for information that is already in the USER PROFILE or MEMORY.
   Look it up first.
4. When a figure required for an answer is missing, ask one specific
   question. Never estimate silently.
5. Show the basis of any calculation you report.
6. Never open a reply with a preamble, a restatement of the question, or a
   summary of what you are about to do.
7. Use the language, units and register named in the USER PROFILE.
</directives>

<user-profile>
{{USER_MD}}
</user-profile>

<memory>
{{MEMORY_MD}}
</memory>
```

## Rendering order

| Order | Block | Source | Changes when |
| --- | --- | --- | --- |
| 1 | Tool list | Generated by the agent runtime | A tool is added, removed or renamed |
| 2 | `<identity>` | This file | Deliberately, rarely |
| 3 | `<directives>` | This file | Deliberately, rarely |
| 4 | `<user-profile>` | `USER.md` | The profile is edited, or a session starts |
| 5 | `<memory>` | `MEMORY.md` | Consolidation promotes a fact, or a session starts |
| 6 | Conversation history | The transcript | Every turn, appended at the tail |
| 7 | Retrieved context | `memory_search` output | Every turn, appended at the tail |

Blocks 1 to 5 are the cacheable prefix. Blocks 6 and 7 are the volatile tail.
Retrieved context belongs in the tail, not in the prefix, because it changes on
every turn and would invalidate the cache for itself.

## Content that must never enter the prefix

- The current date, time or timezone
- A countdown, a "last updated" stamp, or a memory read timestamp
- Session identifiers, request identifiers, message counters
- Anything derived from a tool call in the current turn
- Retrieved memory snippets, unless deliberately pinned
- A live file listing, a git SHA, or a directory tree
- Model names, unless the runtime needs them for routing and pins them anyway

The test for any candidate line is simple: if it would differ between two
consecutive turns of the same session, it does not belong above the tail.

## Where the retrieved context goes

Retrieved memory is evidence, not instruction. It is appended to the tail and
should be wrapped so the model can tell it apart from the user's own words:

```
<retrieved-memory source="MEMORY.md" trust="curated">
...snippets...
</retrieved-memory>
```

Content that arrives from a tool, a web page, or any source outside the
workspace is untrusted regardless of where it sits. The platform's own
provenance model classifies content as `owner`, `agent`, `untrusted` or
`system`, and only the first two are eligible for automatic injection. The
wrapping above is the prompt-side equivalent of that rule.

## Profiling the prefix

| Profile | Typical size | When to use |
| --- | --- | --- |
| Personal assistant | 1.5k to 4k tokens | One person, one agent, direct chat |
| Orchestrator | 4k to 8k tokens | A manager agent that dispatches to workers |
| Worker | 1k to 2k tokens | A specialised agent with a narrow job |

Above roughly 8k tokens the prefix dominates every request and the cache write
cost stops being amortised. If the profile approaches that, the fix is to move
detail out of the prefix into retrieved context, not to raise the budget.
